# agentme-bdr-policy-411: Phase 5 - Develop, Build and Configure

## Context and Problem Statement

Implementation tends to skip the preparation of control automation and to treat testing as one activity. The delivery flow of `agentme-edr-503` separates test groups, and the controls designed in phase 4 need automation and evidence generated by the team.

Question: What is built in phase 5, who is accountable, and what must exist when it ends?

## Decision Outcome

**Phase 5 implements and configures the solution, automates development, infrastructure and controls, and passes group Development in `dev` and `tst` before the build moves to acceptance**

### Details

#### 01-objective-and-entry

The objective is a build that satisfies the requirements of phase 4 and generates the evidence for the controls. The entry MUST be the approved design, or a build returned from phase 6, 7 or 8.

#### 02-activities-and-outputs

Activities and outputs MUST include:

- implementation of the solution and configuration of platforms and third-party services
- development, infrastructure and deployment automation, per `agentme-edr-303`
- control automation: checks that generate the evidence the Control Owner verifies, produced by skills or pipelines
- group Development tests: code reviews, unit, regression, end-to-end and smoke tests, and the preparation of performance tests, which run in `acc` in phase 6 (`agentme-edr-503` rule 02)
- runbooks and monitoring configuration needed by phase 6 operational readiness

#### 03-raci

The activities below MUST be performed with the accountability shown, using the abbreviations of `agentme-bdr-405`.

|---|---|---|---|---|---|---|---|---|---|---|---|---|---|---|---|---|
| Feature or model implementation, including migration, cutover, and legacy decommissioning build work | | | | | C | C | | | | A (non-AI) | A (AI) | | R | R | | |
| Code or model review | | | | | | | | | | A (non-AI) | A (AI) | | | | | |
| Independent QA and test execution | | | | | | | | | | A (non-AI) | A (AI) | | | | | R (Tester/QA) |
| AI model evaluation, safety, and fairness testing | | | | | | C | | | | | A | C | | R | | R (Tester/QA) |
| Dependency and license compliance | | | | | | | | | | A | | C | | | | |
| CI/CD pipeline and deployment automation | | | | | | | | | | A | | | | | R | |

Tech Lead and AI Lead also consult each other on shared (non-AI)/(AI) integration points. Specialist columns (R) apply only when that specialist is engaged (`agentme-bdr-405` rule 05).

#### 04-environments-and-tests

Work MUST run locally, in CI, `dev` and `tst` (`agentme-adr-301`), with synthetic data and no users. The test group is group Development of `agentme-edr-503`; unit tests, linting and the AI test requirements of `agentme-edr-501` apply.

#### 05-xdrs-outputs

Runbooks and operational procedures MUST be written as EDRs of subject operations, and skills that automate development, operation or evidence generation MUST be placed in the scope per `agentme-bdr-416`. The codebase itself MUST NOT be part of XDRS.

#### 06-exit-gate

The Tech Lead MUST confirm that group Development passed (`agentme-bdr-503` rule 01). A failed gate in a later phase returns the build here (`agentme-edr-503` rule 02).
